# Demande à l'API : lot du jour, ordres d'envoi et garde-fous

Écran demandeur : Lot du jour. Besoin : déclencher la préparation du lot, voir ses contrôles et ses blocages, parcourir les ordres produits, libérer un lot bloqué par décision motivée, relire les lots passés. Aucun envoi réel n'existe dans cette version : « prêt » est un simple marquage.

## Opérations
Toutes les routes : garde de profil `supervisor`. Listes : `from`, `size` (1 à 100, défaut 10), `{ items, total }`.

| Méthode et chemin | Action déclarée | Rôles | Entrée (bornes comprises) | Réponses (codes et formes) |
|---|---|---|---|---|
| `GET /daily-batches` | `batches:list` | profil `supervisor` | `from`, `size` | `200 { items: DailyBatchSummaryDto[], total }`, du plus récent au plus ancien (`date` décroissante, puis `createdAt` décroissant : le lot qui en remplace un autre le même jour vient en premier) |
| `GET /daily-batches/:id` | `batches:get` | profil `supervisor` | `id` uuid | `200 { batch: DailyBatchDetailDto }` ; `404 repository.not_found` |
| `GET /daily-batches/:id/orders` | `batches:orders` | profil `supervisor` | `type` ; `channel` ; `from`, `size` | `200 { items: OrderDto[], total }` triés par identifiant client puis type ; `404` |
| `POST /daily-batches` | `batches:prepare` | profil `supervisor` | aucun corps | `201 { batch: DailyBatchDetailDto }` ; `409 batches.already_released` (le lot du jour est déjà `ready`) |
| `POST /daily-batches/:id/release` | `batches:release` | profil `supervisor` | `id` uuid ; corps strict `{ reason: string (rogné, 1..1000) }` | `200 { batch: DailyBatchDetailDto }` ; `400` ; `404` ; `409 batches.not_releasable` (lot qui n'est pas `blocked` : déjà `ready` ou `replaced`) |

DTO :
- `DailyBatchSummaryDto` = `{ id, date, status: 'blocked' \| 'ready' \| 'replaced', preparedBy: { id, email }, createdAt, caseCount: integer, orderCount: integer, failedChecks: integer, releasedBy: { id, email } \| null, releasedAt \| null }`.
- `DailyBatchDetailDto` = `DailyBatchSummaryDto` + `{ checks: BatchCheckDto[], shares: DecisionShareDto[], excluded: { reason: 'documents_missing' \| 'channel_suspended' \| 'channel_not_authorized' \| 'no_contact' \| 'frozen' \| 'statement_stale' \| 'covered_by_outputs', count: integer }[], ordersByType: { type, count }[], releaseReason: string \| null, replacedBy: uuid \| null, policyVersion: { id, label } \| null }`.
- `BatchCheckDto` = `{ code: 'statement_fresh' \| 'witnesses_replayed' \| 'decision_share' \| 'no_duplicate_order', status: 'passed' \| 'failed', problems: string(1..300)[] /* au plus 50, français */ }`.
- `DecisionShareDto` = `{ type: 'none' \| 'reminder' \| 'proposal' \| 'transfer_proposed', count: integer, shareBp: integer /* 0 à 10000 */, mode: 'fixed_cap' \| 'statistical', capBp: integer \| null, meanBp: number \| null, sigmaBp: number \| null, thresholdBp: number \| null, exceeded: boolean }`.
- `OrderDto` = `{ id, type: 'reminder' \| 'proposal' \| 'commitment_confirmation', status: 'planned' \| 'blocked' \| 'cancelled', caseId, debtorId, interlocutorId: uuid, interlocutorRole, channel, conditions: { name: string(1..100), value: string(0..300) }[] /* montants, échéances, offre : jamais de texte rédigé */, blockReason: string \| null, orderDate: date, batchId: uuid \| null }`.

Trace d'audit : `prepare` et `release` sont tracées (type d'objet « Lot du jour », actions `batches:prepare` et `batches:release`, identifiant = id du lot ; résumés « Lot du jour du JJ/MM/AAAA préparé : 120 ordres, prêt. » ou « … bloqué. » et « Lot du jour du JJ/MM/AAAA libéré par décision du superviseur. »).

## Règles
- `rule-recouvrement-batch-prepared-by-supervisor` (user) : le superviseur déclenche la préparation du lot ; aucun ordonnancement automatique n'existe ; les autres profils reçoivent `403 security.access_denied`.
- `rule-recouvrement-batch-brain-decides` (user) : le cerveau décide l'action de chaque dossier non final (ni `settled` ni `transferred`) en évaluant la décision JDM de la politique active (entrée : segment, nature, état, retard maximal, montant négociable, dépassement du seuil) ; chaque décision est journalisée (`rule-recouvrement-decision-journal`) ; sans politique active, `POST /daily-batches` répond `409 batches.no_active_policy`.
- `rule-recouvrement-batch-orders-structured` (user) : le lot produit des ordres d'envoi structurés (dossier, interlocuteur, canal, conditions), sans texte rédigé ; une relance (`reminder`) porte le montant dû de chaque facture visée, ses échéances ; une proposition (`proposal`) porte les conditions de l'ancrage, c'est-à-dire la première offre de l'échelle chiffrée par le cerveau.
- `rule-recouvrement-batch-order-eligibility` (user) : un dossier reçoit un ordre sur un canal si une facture négociable autorise ce canal, si un interlocuteur y est joignable (coordonnée valide, canal non suspendu : `rule-recouvrement-contact-invalid-suspends-channel`) et si la politique n'exige aucune pièce absente de l'index pour la facture visée (`rule-recouvrement-documents-required-blocks-reminder`) ; sinon le dossier est compté dans `excluded` avec sa raison, sans bloquer le lot. Un dossier gelé, ou dont le montant négociable est nul, ne reçoit aucun ordre.
- `rule-recouvrement-batch-channel-order` (inferred) : le canal choisi pour un dossier est le premier canal éligible dans l'ordre `voice`, `email_sms`, `mail` ; l'interlocuteur choisi est le premier, trié par rôle (ordre du référentiel §6) puis par identifiant.
- `rule-recouvrement-documents-required-blocks-reminder` (user) : une pièce exigée par la politique (par segment et nature) et absente de l'index Pièces de la facture bloque la relance de cette facture : elle n'entre pas dans les ordres ; sans facture éligible, le dossier est exclu (`documents_missing`).
- `rule-recouvrement-batch-statement-fresh` (user) : contrôle `statement_fresh` : sans relevé bancaire confirmé frais (`GET /recovery-imports/status`), aucun ordre n'est prévu (le lot est `blocked`, zéro ordre, dossiers exclus `statement_stale`) et le contrôle échoue.
- `rule-recouvrement-batch-witnesses-replayed` (user) : contrôle `witnesses_replayed` : les dossiers témoins de la version active sont rejoués à chaque lot ; un écart (action ou règle différente) fait échouer le contrôle et bloque le lot.
- `rule-recouvrement-witness-no-order` (user) : les dossiers témoins ne produisent jamais d'ordre libérable ; leur rejeu ne crée ni ordre, ni décision rattachée à un dossier réel, ni élément de file, ni transition.
- `rule-recouvrement-batch-release-when-checks-pass` (user) : le lot est libéré quand tous ses contrôles passent ; libéré, il est seulement marqué prêt (`ready`) ; aucun envoi n'existe.
- `rule-recouvrement-batch-release-mode` (user, Q-RECOUVREMENT-04 arbitrée par le propriétaire, decision D-0020) : tous les contrôles passant, le lot devient `ready` dès la préparation (`releasedBy` nul, libération automatique) ; le superviseur n'intervient que pour un lot `blocked`. Il n'existe pas d'état « à libérer ».
- `rule-recouvrement-batch-blocked-release-by-decision` (user) : un lot bloqué ne se libère que par une décision motivée du superviseur (`POST .../release` avec `reason`) ; il devient `ready`, `releaseReason` et `releasedBy` sont conservés, les contrôles en échec restent affichés.
- `rule-recouvrement-batch-one-per-day` (inferred) : un seul lot actif par date (index unique partiel de la base sur la date hors `replaced`) ; une nouvelle préparation le jour même remplace un lot `blocked` (il passe à `replaced`, ses ordres à `cancelled`, `replacedBy` renseigné) ; si le lot du jour est `ready`, `409 batches.already_released`.
- `rule-recouvrement-batch-no-duplicate-order` (user) : un seul ordre actif par dossier, type et jour, garanti par la base (index unique partiel sur dossier, type, date de l'ordre hors `cancelled`) ; une tentative de doublon ne produit aucun second ordre et le contrôle `no_duplicate_order` rapporte le nombre de doublons écartés (il n'échoue pas : la base les a empêchés).
- `rule-recouvrement-batch-auto-stop` (user) : contrôle `decision_share` : la part de chaque type de décision (`none`, `reminder`, `proposal`, `transfer_proposed`) dans le lot (nombre de décisions de ce type sur le nombre de dossiers décidés) est comparée à sa moyenne sur les 20 derniers lots précédents (hors `replaced`) dès qu'il en existe au moins 10 : un écart absolu à la moyenne strictement supérieur à trois écarts-types bloque le lot ; avant 10 lots, le plafond fixe du type (`decisionTypeCapsBp` de la politique) s'applique (part strictement supérieure au plafond : blocage). Un blocage ouvre un élément de file `alert` (une seule par lot).
- `rule-recouvrement-decision-share-sigma` (inferred, default Q-RECOUVREMENT-09, decision D-0005) : l'écart-type est celui de la population des lots retenus (division par n) ; avec un écart-type nul, toute part différente de la moyenne bloque.
- `rule-recouvrement-exposure-ceiling` (user) : plafond d'encours sous échéancier par version d'agent et par segment (`exposureCeilings`, `*` pour tous) : l'encours est la somme des restes à payer des engagements `pending` à échéancier ; quand il atteint le plafond, aucune offre à échéancier n'est plus rendue (`outils-agents`) et un élément `alert` s'ouvre (un par version d'agent et segment tant que le plafond reste atteint). Un lot ne propose pas non plus d'ordre `proposal` à échéancier dans ce cas (l'ancrage est alors la première offre sans échéancier).
- `rule-recouvrement-company-transfer-proposed` (inferred, default Q-RECOUVREMENT-07, decision D-0003) : l'action du jour `transfer_proposed` d'un dossier d'entreprise ouvre un élément de file `transfer_proposed` (état `supervisor_queue`) comme pour une famille ; seule la décision du superviseur le transfère.
- `rule-recouvrement-commitment-confirmation-immediate` (user) : la confirmation écrite d'un engagement est un ordre `commitment_confirmation` émis immédiatement, hors lot (`batchId` nul), soumis aux mêmes contrôles unitaires que les ordres du lot (relevé frais, canal autorisé et joignable, aucun doublon du jour, dossier non gelé hors l'engagement lui-même) ; refusé par un contrôle, l'ordre est `blocked` avec sa raison (`blockReason`).
- `rule-recouvrement-confirmation-blocked-alert` (inferred) : une confirmation d'engagement refusée par un contrôle unitaire ouvre un élément de file `alert` (un par ordre) ; l'engagement reste inscrit (la réponse de l'outil le dit par `confirmationOrder.status: 'blocked'`).
- `rule-recouvrement-batch-families-no-transfer` (user) : voir `rule-recouvrement-family-transfer-never-executed` ; un lot ne transfère jamais un dossier de famille.
- `rule-recouvrement-batch-prescription-flow` (user) : la préparation du lot constate la prescription (`rule-recouvrement-prescription`).

## Compatibilité
Aucune opération existante modifiée. Tables nouvelles : lots, ordres, décisions du cerveau (voir le plan du module). `specifications/permissions.yaml` : une ligne par opération.
