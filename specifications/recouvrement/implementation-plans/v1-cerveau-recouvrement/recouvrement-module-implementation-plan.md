# Module recouvrement : plan de réalisation

Version `v1-cerveau-recouvrement`. Plan de l'agent de fabrication du backend. Il s'appuie sur les demandes à l'API du frontend du même dossier (une par fonctionnalité, citées entre parenthèses) et sur `referentiel-etats-et-transitions.md` ; les schémas Zod, les bornes, les formes de réponse et les codes d'erreur **sont ceux de ces demandes** (elles ne sont pas recopiées ici : toute divergence se corrige dans la demande, pas dans le code). Le plan fixe ce que les demandes laissent au module : tables, contraintes de base, découpage, mécanismes, ordre de fabrication, tests. Aucun code n'est écrit par ce plan.

La provenance de chaque règle est celle écrite en amont (`user`, `inferred`, `inferred, default Q-RECOUVREMENT-NN, decision D-00NN`). Les règles que ce plan ajoute lui-même sont marquées `(inferred)` ou `(inferred, default Q-RECOUVREMENT-NN, decision D-00NN)`. Les vingt questions de `questions.yaml` (13 à 20 ajoutées par ce plan ; 01 à 12 venues du frontend) sont toutes arbitrées dans `specifications/recouvrement/arbitrages.yaml` : ce plan construit **l'option arbitrée** de chacune (aucun reste d'option écartée, en particulier : pas d'état de lot « à libérer » (Q-04), pas de transfert exécuté par le cerveau pour une entreprise (Q-07)). Les cinq règles dont le propriétaire a lui-même tranché la question (Q-01 à Q-05, décisions D-0017 à D-0021) sont étiquetées `(user, …)` : sa réponse vaut énoncé ; les quinze autres restent `(inferred, default …)`.

Lecture de « vérifiée par le serveur et par la base, à chaque requête » : le serveur lit le profil en base à **chaque** requête (jamais dans le jeton) et la base porte elle-même les invariants de droits et d'intégrité qui ne dépendent pas du code (un compte agent par canal, rôle `user` obligatoire pour un compte agent, journaux en ajout seul, un seul ordre par dossier, type et jour, une seule version active, un seul litige ouvert par facture…). Il n'y a pas de rôle PostgreSQL ni de politique de ligne par profil : l'application se connecte avec un seul rôle, et un profil ne se traduit pas en droits SQL (voir R9).

## Découpage en fonctionnalités

Nouveaux dossiers `api/src/features/<feature>/` (module, controller, service, schemas, tables, `tests/`), chacun ajouté à `api/src/app.module.ts` (non gelé). Les dossiers gelés (`platform`, `auth`, `users`, `groups`, `scopes`, `audit`, `imports`, `main.ts`, `scripts`) ne sont pas modifiés ; leurs exports peuvent être importés.

| Fonctionnalité | Contenu | Demande |
|---|---|---|

| `cases` | débiteurs/dossiers, factures, gels, historique d'états, service d'états, montant négociable, 6 routes de lecture | `dossiers`, référentiel |

Dépendances de code, **sans cycle de modules Nest** (pas de `forwardRef`). Le cerveau écrit dans la file (`QueueService.open`), dans les sorties comptables (`LedgerService.createDiscountCredit`) et lit les litiges ; en retour la décision de la file, la clôture d'un litige et l'approbation d'une sortie rappellent `brain.evaluate`. Pour ne pas fermer la boucle, chacune de ces trois fonctionnalités est coupée en deux modules Nest : un **noyau** (tables, écrivains appelés par le cerveau : `QueueService.open`, `LedgerService.createDiscountCredit`/`recognize`, `DisputeWriter.openFromContestation`/`openFromImport`) qui ne dépend que de `cases`, et des **actions** (contrôleur, services de décision, d'approbation, de clôture) qui dépendent du cerveau. Ordre, du bas vers le haut :
1. `profiles`, `cases`, `policies` ;
2. noyaux `decision-queue-core`, `ledger-core`, `disputes-core` ;
3. `negotiation` (offres, engagements, échéances), puis `brain` (importe les noyaux, `negotiation`, `policies`, `cases`) ;
4. actions `decision-queue`, `ledger`, `disputes` (importent `brain`) ;
5. points d'entrée : `recovery-imports`, `agent-tools`, `batches`, `reviews`, `indicators`.
Les services du bas ne dépendent jamais des contrôleurs ; les événements qui touchent plusieurs fonctionnalités passent par `brain.evaluate(...)` (voir Règles transverses). Un test de dépendances (`madge` ou lecture des `imports:` des modules) échoue sur tout cycle. Dépendances npm nouvelles de `api/` : `@gorules/zen-engine`, `@modelcontextprotocol/sdk`.

## Données

Tout dans le schéma `base`, une `*.tables.ts` par fonctionnalité, `pnpm migrate:gen && pnpm migrate:all`. Aucune table contractuelle n'est modifiée ; les tables ci-dessous sont des ajouts au contrat de données (contestation à ouvrir, voir plus bas). Convention : montants `bigint` en centimes avec `mode: 'number'` (toutes les bornes de l'API tiennent dans 2^53), dates métier `date`, instants `timestamptz`, énumérations en `text` avec contrainte `CHECK` (codes du référentiel §1 à §6) pour ne pas figer de types Postgres. Aucune table n'est rattachée à un périmètre (`scope_code` absent : l'accès repose sur les profils, demande `dossiers`, Compatibilité).

### Profils (`profiles.tables.ts`)
- `user_profiles` : `user_id` uuid PK, FK `base.users(id)` ON DELETE CASCADE ; `profile` text CHECK (`supervisor`, `agent`, `litigation`, `indicators`) ; `channel` text null CHECK (`voice`, `email_sms`, `mail`) ; `created_at`, `updated_at`. CHECK `(profile = 'agent') = (channel IS NOT NULL)`. Index unique partiel sur `channel` WHERE `profile = 'agent'` (`rule-recouvrement-agent-one-per-channel`). Déclencheur `BEFORE INSERT OR UPDATE` refusant un profil `agent` sur un compte dont `base.users.role <> 'user'`, et déclencheur sur `base.users` (`AFTER UPDATE OF role`) refusant le passage à `admin` d'un compte ayant un profil `agent` (ajout de déclencheurs, aucune colonne du contrat modifiée ; `PATCH /users/:id`, gelé, n'est pas adapté : voir « Risques », R6). Un seul profil par compte = la clé primaire (Q-RECOUVREMENT-02, option A).

### Dossiers (`cases.tables.ts`)
- `cases` : `id` uuid PK ; `debtor_id` text UNIQUE (1 à 50) ; `nature` CHECK (`family`, `company`) ; `debtor_siren` text null, CHECK `(nature = 'company') = (debtor_siren ~ '^[0-9]{9}$')` ; `segment` text CHECK `^[a-z0-9][a-z0-9_-]{0,49}$` ; `state` CHECK (7 états) ; `state_since` ; `transferred_at` null ; `transfer_kind` null ; `authorized_cents` bigint null (montant autorisé par `authorize`) ; `first_seen_on` date ; `first_seen_due_cents` bigint ; `first_policy_version_id` uuid null (version active à la première apparition, pour l'indicateur « encaissé / dû ») ; `rejected_transfer_rule` text null (règle au moment d'un `reject_transfer`) ; `created_at`, `updated_at`. Index sur `(state)`, `(segment)`.
- `invoices` : `id` PK ; `case_id` FK ; `kind` CHECK (`invoice`, `credit_note`) ; `number` (1 à 50) ; `creditor_siren` CHECK 9 chiffres ; UNIQUE `(creditor_siren, number)` ; `amount_cents`, `imported_balance_cents` (solde du dernier cliché), `balance_cents` (solde courant = solde du cliché moins les paiements appliqués postérieurs à l'extraction) ; `payer` text null ; `invoice_date`, `due_date` ; `channels` text[] (sous-ensemble des trois canaux) ; `closed_at` null ; `first_seen_on`, `first_seen_balance_cents` ; `last_extraction_date` ; `payer`. CHECK de signe : facture `amount > 0` et `0 <= balance <= amount` ; avoir `amount < 0` et `amount <= balance <= 0` ; `due_date >= invoice_date` ; valeurs absolues bornées à 10 000 000 000. Index `(case_id)`, `(number text_pattern_ops)` pour la recherche par préfixe.
- `freezes` : `id`, `case_id`, `code` CHECK (`dispute`, `contestation`, `unassigned_payment`), `scope` (`invoice`, `case`), `invoice_id` null (obligatoire ssi `scope = 'invoice'`), `source_type`, `source_id` (litige, contestation ou affectation de paiement), `reference` text (1 à 100), `since`, `released_at` null. Index unique partiel `(case_id, code, source_type, source_id) WHERE released_at IS NULL`. Le gel est une ligne, jamais recalculée à la lecture (`FreezeDto`).
- `case_state_history` : `id` bigserial, `case_id`, `at`, `from_state` null, `to_state`, `cause`, `actor` text (1 à 200), `reference` null. Déclencheurs refusant `UPDATE` et `DELETE` (comme `audit_logs`, TRUNCATE permis seulement dans une base `*_test`).
- `receivable_snapshots` : `id`, `import_id` FK `base.import_previews(id)` (le socle conserve la ligne confirmée), `extraction_date` UNIQUE, `control_total_cents`, `total_cents`, `confirmed_at`.

### Imports (`recovery-imports.tables.ts`)
**Réutilisation du socle, pas de seconde mécanique d'aperçu.** Les tables d'aperçu du socle (`import_previews`, `import_preview_rows`, `import_preview_errors`, exportées par `features/imports/imports.tables.ts`) portent déjà : l'auteur, l'empreinte du fichier, l'unicité « un fichier confirmé une seule fois » par `feature` (index unique partiel, `409 import.already_imported`), l'expiration à 2 heures et la purge, les lignes préparées, les erreurs paginées, les compteurs et les dates de confirmation. Chaque type d'import de recouvrement y est une `feature` : `recovery-receivables`, `recovery-payments`, `recovery-disputes`, `recovery-contacts`, `recovery-documents`. Aucune table `recovery_imports`, `recovery_import_rows` ni `recovery_import_errors` n'est créée. Deux voies :
- **`disputes`, `contacts`, `documents`** (importés par leurs lignes valides, comme le socle) : une `ImportDefinition` chacune, exactement sur le modèle de `users/users-import.*`, et les méthodes `ImportsService.specification | preview | errors | confirm` appelées telles quelles par le contrôleur de `recovery-imports`. `checkBatch` porte les contrôles contre la base (facture inconnue ou ambiguë, débiteur inconnu, rôle incompatible avec la nature), `saveBatch` l'écriture (litige et gel, interlocuteurs, index des pièces). `uniqueKey` du socle est une clé d'**une** colonne : les doublons à clé composée (entité + numéro [+ type], débiteur + rôle + coordonnées) n'en relèvent pas ; la première ligne l'emporte et les suivantes sont **ignorées** à `saveBatch` (`ON CONFLICT DO NOTHING` sur les index uniques, comptées dans `skippedCount` et signalées par la note `duplicates` du rapport), jamais une erreur de ligne. Le rapport d'écarts et les effets s'ajoutent *autour* de ces appels (voir plus bas) : rien n'est recopié.
- **`receivables`, `payments`** (refus entier à la première erreur, total de contrôle, date d'extraction et débiteur cohérents entre lignes) : ces contrôles de fichier ne tiennent pas dans `ImportDefinition`. Un `WholeFileImportService` propre à la fonctionnalité fait l'analyse, mais réutilise : `receiveUpload` (réception en flux vers un fichier temporaire, le total de contrôle étant un paramètre de requête, donc aucun second analyseur multipart), `inspectXlsx`, `readRows`, `isBlankRow`, `echo`/`fitReason`, `MAX_FILE_BYTES`, `MAX_ROWS`, `ACCEPTED_EXTENSIONS`, les erreurs de `imports.errors.ts`, et écrit dans **les tables d'aperçu du socle** (`import_previews` avec `feature`, `import_preview_rows` pour les lignes préparées, `import_preview_errors` pour l'unique erreur). Seules trois petites fonctions privées de `ImportsService` ne sont pas exportées et sont recopiées avec leur référence (`sniff` : extension contre contenu ; lecture de l'en-tête ; décompte des lignes) : ≈ 60 lignes, à signaler en commentaire `copie de ImportsService.<fonction>` ; `features/imports/` étant gelé, les exporter n'est pas possible.
Tables propres, rattachées aux aperçus du socle par une clé étrangère `ON DELETE CASCADE` (la purge des aperçus expirés les emporte) :
- `recovery_import_details` : `import_id` uuid PK, FK `base.import_previews(id)` ; `accepted` bool ; `extraction_date` date null ; `control_total_cents` bigint null ; `computed_total_cents` bigint null ; `effects` jsonb null (au plus 20 `{label, count}` écrits à la confirmation). Les types « lignes valides » y ont `accepted = true` et le reste à `null`.
- `recovery_import_report_items` : `import_id` (FK `base.import_previews(id)`), `category` (`new`, `settled`, `modified`, `removed`), `key` (1 à 200), `debtor_id` null, `detail` (1 à 300), PK `(import_id, category, key)`, plus `recovery_import_report_notes` (`import_id`, `code`, `label`, `count`). Calculé à l'aperçu, conservé après confirmation (lecture d'un import confirmé ; les lignes de l'aperçu, elles, sont supprimées par le socle à la confirmation).
L'historique (`GET /recovery-imports/history`) et `GET status.lastConfirmed` se lisent dans `import_previews` (`feature LIKE 'recovery-%'`, `status = 'confirmed'`), jointure sur `base.users` pour `confirmedBy`.
- `payments` : `id`, `reference` text (1 à 100) UNIQUE, `amount_cents` > 0, `payment_date`, `statement_date`, `import_id` (FK `base.import_previews(id)`), `status` (`already_in_balances`, `applied`) ; `statements` : `statement_date`, `import_id` (même FK), `confirmed_at` (fraîcheur).
- `payment_allocations` : `id`, `payment_id` FK, `invoice_id` FK null (nul = non affecté), `amount_cents` > 0, `origin` CHECK (`reference`, `amount`, `excess`, `supervisor`), `parent_allocation_id` null (excédent), `created_at`, `assigned_by` null, `assigned_at` null. Le solde courant d'une facture = `imported_balance_cents` moins la somme de ses affectations dont le paiement est postérieur à l'extraction. Le lettrage automatique (origines `reference`, `amount`, `excess`) est recalculé en entier à chaque confirmation de Créances ou de Paiements, les affectations `supervisor` étant appliquées d'abord et conservées (`rule-recouvrement-unassigned-payment-freeze`).
- `contacts` : `id` uuid (conservé quand `(case_id, role, email, phone, postal_address)` est inchangé), `case_id`, `role` CHECK (4), `email`, `phone`, `postal_address` (null possibles, au moins une renseignée), `suspended_channels` text[] ; UNIQUE `(case_id, role, coalesce(email,''), coalesce(phone,''), coalesce(postal_address,''))`.
- `invoice_documents` : `invoice_id`, `type` CHECK (3), `reference` null, PK `(invoice_id, type)`.

### Litiges (`disputes.tables.ts`)

### Sorties comptables (`ledger.tables.ts`)
- Séquence `ledger_reference_seq` ; `ledger_outputs` : `id`, `reference` text UNIQUE DEFAULT `'SC-' || lpad(nextval(...)::text, 6, '0')` (jamais réutilisée), `type` CHECK (`discount_credit`, `write_off`), `origin` (`commitment`, `supervisor`), `status` CHECK (4), `creditor_siren`, `case_id`, `commitment_id` null, `amount_cents` > 0, `reason` (1 à 500), `created_at`, `approved_by` null, `approved_at` null, `recognized_at` null, `imports_since_approval` int >= 0. `ledger_output_lines` (`output_id`, `invoice_id`, `amount_cents` > 0, PK composite). Un avoir de remise et un passage en perte sont rattachés à une seule entité créancière (CHECK via la facture à la création, vérifié par le service).

### Lots (`batches.tables.ts`)
- `daily_batches` : `id`, `batch_date` date, `status` CHECK (`blocked`, `ready`, `replaced`), `prepared_by`, `created_at`, `released_by` null, `released_at` null, `release_reason` null, `replaced_by` null, `policy_version_id` null, `case_count`, `checks` jsonb, `shares` jsonb, `excluded` jsonb. Index unique partiel `(batch_date) WHERE status <> 'replaced'` (`rule-recouvrement-batch-one-per-day`).
- `send_orders` : `id`, `batch_id` null, `type` CHECK (3), `status` CHECK (`planned`, `blocked`, `cancelled`), `case_id`, `interlocutor_id`, `channel`, `conditions` jsonb (`[{name, value}]`, jamais de texte rédigé), `block_reason` null, `order_date` date, `created_at`. Index unique partiel `(case_id, type, order_date) WHERE status <> 'cancelled'` : c'est la garantie « aucun envoi en double » côté base (`rule-recouvrement-batch-no-duplicate-order`, même condition que la demande `lot-du-jour`) ; un ordre `blocked` (confirmation refusée par un contrôle unitaire) occupe donc sa place du jour et n'est jamais libérable ; seuls les ordres d'un lot remplacé passent à `cancelled` et libèrent la place.

### Migrations
Une migration par fonctionnalité dans l'ordre de fabrication (profils d'abord), plus une migration d'écriture de déclencheurs (`CREATE FUNCTION` / `CREATE TRIGGER` en SQL brut dans le fichier généré). Le déclencheur « append-only » du socle (`0001_audit_append_only`) sert de modèle, y compris l'exception TRUNCATE des bases `*_test`. `resetData()` des tests tronque toutes les tables de `base` : les nouvelles tables doivent donc être tronquables en base de test (vérifier que le helper les énumère ou qu'il lit le catalogue ; sinon contestation `OPEN: acceptance`, helper en `platform/testing/helpers.ts` gelé).

## Opérations

Convention d'accès : « garde P » = `@Access({ action, roles: [] })` + `@UseGuards(RequireProfile('P'))`. `RequireProfile` (dans `profiles/profile.guard.ts`, sur le modèle de `SelfOrAdminGuard` de `features/users/users.guards.ts`) lit `user_profiles` **à chaque requête** (jamais le jeton), répond `401` sans jeton, `403 security.access_denied` si le profil manque ou diffère, **avant** toute validation et lecture de corps, sans révéler l'existence de l'objet (`rule-recouvrement-profile-server-enforced`). Un compte `admin` sans profil est refusé (Q-RECOUVREMENT-01, option A) ; un `admin` portant un profil exerce celui-ci. Schémas, bornes et codes d'erreur : ceux de la demande citée. Chaque `POST`/`PUT` est `@Audited` (objet et résumé donnés par la demande) ou `@AuditExempt('<raison>')`. Les routes statiques sont déclarées **avant** les routes à `:id` du même contrôleur (`/cases/filters`, `/disputes/invoices`, `/ledger-outputs/counts|export`, `/recovery-imports/history|status`, `/decision-queue/counts`, `/indicators/filters`).

### Points de conception par fonctionnalité

**Profiles.** `PUT` en transaction : refuse l'auto-modification (`409 profiles.cannot_change_own_profile`), exige `channel` pour `agent` et le refuse ailleurs, refuse `agent` sur un compte non `user`, traduit la violation de l'index unique partiel en `409 profiles.channel_taken` ; `profile: null` supprime la ligne et rend `{profile: null, channel: null}`. `GET /user-profiles` ne rend que les comptes ayant un profil, triés par e-mail (`byLowerText`).

**Cases.** `CaseStateService.recompute(caseId, cause, actor, reference, tx)` est l'unique écrivain de `cases.state` : il évalue la précédence du référentiel §1 (`settled`, `transferred`, `frozen`, `supervisor_queue`, `committed`, `negotiating`, `open`), n'écrit une ligne d'historique que si l'état change, vérifie la transition contre le tableau du référentiel §2 (une transition absente lève une erreur interne `500` testée, jamais produite : `rule-recouvrement-case-state-referential`) et s'exécute dans la transaction de l'événement (`rule-recouvrement-state-transitions-logged`). `GET /cases` filtre par `state`, `nature`, `segment`, `creditor` (SIREN d'une facture), `search` (sous-chaîne sans casse sur `debtor_id`, caractères `%` et `_` échappés), trie par montant négociable décroissant puis `debtor_id` (`byText`) ; le montant négociable et `maxDaysLate` sont calculés en SQL (agrégat sur `invoices` et `freezes`), pas stockés. `GET /invoices` : préfixe sans casse, factures `kind = invoice`, `balance > 0`.

**Recovery-imports.** Une définition par type (colonnes du format pivot, noms comparés rognés sans casse, dates `AAAA-MM-JJ` ou `JJ/MM/AAAA`, montants convertis en centimes sans arrondi) ; les cinq types partagent un seul `RecoveryImportsController` (routes de la demande) qui aiguille vers `ImportsService` (`disputes`, `contacts`, `documents`) ou vers `WholeFileImportService` (`receivables`, `payments`) selon le type (voir Données). `receivables` et `payments` : analyse arrêtée à la première erreur (`errorRows = 1`, une entrée), `accepted: false`, `confirm` répond `409 imports.file_refused`. Le total de contrôle est le paramètre de requête `controlTotal` (schéma Zod de la route : texte de motif `^-?[0-9 ]{1,15}([.,][0-9]{1,2})?$`, requis pour `receivables`, refusé pour les autres types) ; le contrôle du total se fait après la lecture complète du fichier. Cohérence entre lignes d'un même débiteur : table de hachage clé `debiteur_id` (nature, SIREN, segment de la première ligne) ; avec un million de lignes la mémoire est bornée par le nombre de débiteurs, ce qui est acceptable et mesuré à la fabrication ; si ce n'est pas le cas, repli sur une table temporaire indexée. **Rapport d'écarts** : écrit par le contrôleur *après* le retour de `ImportsService.preview` (types par lignes : comparaison des lignes préparées de `import_preview_rows` à l'état courant des tables, qui est celui du dernier import confirmé du même type) ou par `WholeFileImportService` pendant l'analyse (`receivables` : comparaison du cliché au portefeuille courant ; `payments` : références déjà connues) ; il ne s'écrit que dans `recovery_import_report_items`/`_notes`, aucune table métier. **`confirm`** : une seule transaction, celle de la route tracée (`ImportsService.confirm` s'y emboîte en point de sauvegarde ; pour les deux types à refus entier, `SELECT ... FOR UPDATE` sur l'aperçu et index unique du socle) qui, pour `receivables`, remplace le portefeuille (`rule-recouvrement-receivables-snapshot`) puis appelle dans l'ordre : lettrage rejoué, constat des sorties (`ledger.recognize`), évaluation de tous les dossiers touchés (`brain.evaluateMany`) ; pour `disputes` : gels puis `brain.evaluateMany` des dossiers touchés ; pour `contacts` et `documents` : recalcul des canaux suspendus / de l'éligibilité, sans évaluation ; `recovery_import_details.effects` est écrit dans la même transaction. `409 imports.stale_extraction` si un cliché plus récent est confirmé entre-temps (verrou consultatif sur `receivable_snapshots`). `GET status` : `fresh` = relevé confirmé le plus récent et `aujourd'hui (Europe/Paris) − lastStatementDate ≤ maxAgeDays` de la politique active ; faux sans politique active.

**Policies.** `PolicyEngine` (service) enveloppe `@gorules/zen-engine` : compile le graphe `decision` d'une version (`createDecision`), évalue `{segment, nature, state, daysLateMax, negotiableCents, overThreshold}`, normalise la sortie `{action, rule}` (sans correspondance : `none` / `no_rule`), met en cache par identifiant de version, est utilisé identiquement pour les témoins et pour les dossiers réels, et n'a aucun accès à la base ni au réseau (le graphe JDM est refusé s'il contient autre chose que des nœuds de décision et d'expression : liste blanche des types de nœud, testée). Les six contrôles sont des fonctions pures `(document, créances confirmées) → {passed, problems}` dans `policy-checks.ts`, exécutées à l'aperçu, à la lecture et à l'activation. Activation : transaction, verrou sur la ligne active et sur la version, six contrôles, ancienne version `superseded`, nouvelle `active`, `409 policies.activation_blocked` avec `details: [{path: code, reason}]` ; l'aperçu JSON est lu en flux de 2 097 152 octets au plus (`413 policies.file_too_large`) et décodé en UTF-8 strict (`400 policies.invalid_file_type`). L'empreinte SHA-256 est calculée sur les octets du fichier. Aucune valeur métier n'apparaît dans le code : bornes de validation du fichier de politique mises à part (elles sont de la validation de format, dans le schéma Zod du fichier), toute grandeur vient du document (`rule-recouvrement-policy-no-business-value-in-code`, vérifié par un test qui recherche les littéraux numériques et les listes de codes dans `brain/`, `negotiation/`, `batches/`, `ledger/`, `agent-tools/`). Liste blanche des seules constantes admises, chacune nommée dans un fichier `constants.ts` par fonctionnalité avec la phrase de la demande qui la fixe : les paramètres de l'arrêt automatique que la demande écrit en dur (trois écarts-types, 20 derniers lots, 10 lots minimum : `rule-recouvrement-batch-auto-stop`) ; l'unité des points de base (10 000) ; la durée de conservation d'un aperçu (2 heures, socle) ; les bornes de format (longueurs, 100 lignes de facture, 500 sorties par approbation) qui sont des bornes de contrat ; les codes d'énumération du référentiel (états, types de file, canaux, natures). Tout autre littéral est une erreur du test.

**Brain.** `BrainService` expose : `evaluate(caseId, trigger, tx)` et `evaluateMany`, appelés aux points de `rule-recouvrement-evaluation-points` (confirmation d'import, préparation de lot, appel d'outil d'agent, clôture de litige, décision du superviseur) ; il enchaîne, dans une transaction par dossier et dans cet ordre : (1) prescription (dates, éléments `prescription_near`/`prescription_expired` une fois par facture, décision `prescription`) ; (2) engagements (tenu, rompu, `commitment_check`) ; (3) gels de dossier (toutes factures gelées) ; (4) seuil (`amount_over_threshold`, décision `threshold`, mémoire de `authorized_cents`) ; (5) plafonds d'encours (décision `exposure_ceiling`, alerte) ; (6) `CaseStateService.recompute`. L'action du jour n'est décidée que par le lot (`DailyActionService`). `OfferService` calcule une offre à partir de la règle (arrondi à la moitié supérieure en arithmétique entière : `(valueBp × negotiable + 5000) / 10000` en `bigint`, jamais de flottant) et applique `rule-recouvrement-offer-computation`. `ClockService.today()` rend la date civile Europe/Paris (`Intl.DateTimeFormat` ou arithmétique de fuseau sans dépendance), seul point d'accès à l'heure pour les règles métier.

**Agent-tools.** Les huit opérations appellent des services `AgentToolsService.<outil>(ctx, input)` qui ne connaissent pas le transport ; `AgentController` (REST) et `McpService` (MCP) sont deux enveloppes minces (`rule-recouvrement-agent-two-transports`). Mécanisme d'appel (`AgentCallRunner`) :
1. `AgentProfileGuard` (garde `agent`, profil lu en base) puis `AgentContextGuard` : valide les quatre en-têtes (`X-Agent-Version`, `X-Channel`, `X-Conversation-Id`, `Idempotency-Key`) **avant** la validation du corps : `400 agent.missing_context` ; `X-Channel` différent du canal du compte : `403 agent.channel_mismatch`.
2. Dans la transaction de la route (celle de l'audit pour une écriture, une transaction propre pour la lecture) : recherche de `(account_id, outil, clé)` ; trouvée avec la même empreinte (SHA-256 des entrées validées et du dossier visé) : réponse enregistrée rejouée avec l'en-tête `Idempotent-Replayed: true` et sans nouvel effet ; trouvée avec une empreinte différente : `409 agent.idempotency_conflict`.
3. Sinon exécution, puis insertion de la ligne `agent_calls` **dans la même transaction que l'effet**. Deux appels simultanés de même clé : l'un des deux échoue à l'index unique `(account_id, tool, idempotency_key)` à la validation ; son effet est annulé et un filtre d'exceptions de contrôleur (`AgentCallFilter`, `@UseFilters` sur les contrôleurs agent) relit l'appel gagnant et rend sa réponse en rejeu : un seul effet.
4. Refus (`ApiError` de statut < 500) : la transaction d'audit est annulée avec l'effet, donc `AgentCallFilter` écrit la ligne de refus (`agent_calls`, `ON CONFLICT DO NOTHING`) par une connexion du pool **après** l'annulation (aucune connexion n'est tenue pendant l'écriture), puis délègue au formatage d'erreur du socle ; un refus rejoué avec la même clé rend le même refus. Les `5xx` ne sont pas conservés. Les refus des gardes (`401`, `403` de profil) précèdent l'identification du compte agent et ne sont pas journalisés.
5. `McpService` : `POST /mcp` répond toujours `200` pour un outil (le résultat porte `isError`) ; chaque outil s'exécute dans un point de sauvegarde (`db.transaction` imbriqué) : en cas de refus, l'effet est annulé, la ligne de refus est écrite dans la transaction de la route (qui est validée) et le résultat est `isError: true` avec `structuredContent = { status, code, message }` identique au corps REST. Le transport est celui du SDK (`@modelcontextprotocol/sdk`, Streamable HTTP sans état, réponse JSON) ; la requête express est convertie vers l'interface Web du transport du SDK si la version installée l'offre, sinon via une enveloppe de réponse minimale ; `GET /mcp` et `DELETE /mcp` sont déclarées cachées du contrat (`hidden: true`) derrière la garde `agent` et répondent `405` avec `Allow: POST` (`rule-recouvrement-mcp-405-after-auth`, plus bas). Le corps `POST /mcp` est déclaré comme objet libre de 1 Mio au plus, sans `rawBody` (le JSON est lu par l'intercepteur de validation). Trois contraintes de la plateforme à respecter, car `POST /mcp` est une route **tracée** (`AuditInterceptor`, `platform/audit/`) :
   - l'intercepteur exige que le **handler retourne** la valeur de la réponse (il la contrôle contre le premier schéma 2xx puis écrit l'entrée d'audit dans la même transaction) ; or le transport du SDK écrit lui-même sur `res`. `McpService` lui donne donc une enveloppe de réponse qui **capture** statut, en-têtes et corps JSON-RPC sans rien écrire sur la vraie réponse ; le handler `@Res({ passthrough: true })` recopie le statut et retourne le corps capturé ;
   - un message JSON-RPC qui est une notification ou une réponse (`notifications/initialized`) doit recevoir `202` sans corps (spécification Streamable HTTP, que le client du SDK attend) : le schéma 2xx de la route est donc `z.any()` (corps opaque, accepte l'absence de valeur) et le handler fixe le statut `202` pour ce cas ; `200` sinon (`@HttpCode(200)`) ;
   - chaque message JSON-RPC reçu avec succès (y compris `initialize` et `tools/list`) laisse une entrée d'audit `agent:mcp` ; `describe` n'utilise que le nom de la méthode et, pour `tools/call`, le nom de l'outil (« Appel MCP : outil report_dispute »), jamais d'argument. Les appels d'outil sont en outre journalisés dans `agent_calls`, comme pour REST.
   Le rejeu d'un appel d'écriture (`Idempotent-Replayed: true`) doit être reconnu par `describe` (résumé « Appel d'agent rejoué ») : `AgentCallRunner` marque l'objet réponse retourné par une propriété à clé `Symbol` (non énumérable, donc absente du JSON et du contrôle de schéma), que `describe` lit.
6. `AgentAccessService.caseVisibleToAgent(caseId, channel, interlocutorId)` : dossier ni `settled` ni `transferred`, une facture négociable autorise le canal, interlocuteur joignable ; sinon `404 cases.not_found` (Q-RECOUVREMENT-08, option A). Chaque réponse agent est construite par des projections dédiées (`AgentCaseDto`, `AgentOfferDto`…) qui ne lisent jamais le segment, la règle, la version de politique, le rang ni les montants de référence ; un test de propriété vérifie qu'aucune clé interdite ne figure dans aucune réponse.
7. `MessageChecker` : analyse (montants, dates, termes internes) selon `rule-recouvrement-message-parsing`, comparée aux conditions débloquées (Q-RECOUVREMENT-11, option A) ; extraits tronqués à 100 caractères, 50 violations au plus.

**Disputes.** Ouverture/clôture dans une transaction avec gel/dégel (`freezes`), recalcul d'état et `brain.evaluate` ; la clôture lève le gel de dossier `contestation` quand le dernier litige né de cette contestation est clos. `GET /disputes/:id` ne rend que le résumé de dossier prévu (jamais la fiche).

**Decision-queue.** `QueueService.open(type, caseId, objectKey, summary, details, tx)` est l'unique créateur d'éléments (`INSERT ... ON CONFLICT DO NOTHING` sur l'index unique) ; `decide` verrouille l'élément (`FOR UPDATE`), contrôle la décision permise par type (table de configuration `queue-types.ts` du référentiel §4, source unique de `allowedDecisions`), le motif (rogné, 1 à 1 000), `invoiceId` (obligatoire seulement pour `assign`), applique les effets de `rule-recouvrement-queue-effects` et recalcule les dossiers touchés. Deux décisions simultanées : le verrou sérialise, la seconde reçoit `409 queue.already_decided`. `candidates` d'un paiement non affecté : au plus 50 factures ouvertes dont le solde ou le total de dossier correspond au montant.

**Ledger.** `LedgerService.createDiscountCredit(commitment, tx)` (appelé par le cerveau quand un engagement assorti d'une remise est tenu : une sortie par entité créancière, remise répartie au prorata des soldes à l'inscription, reliquat sur la facture au plus grand solde), `approve(ids)` (tout ou rien, `FOR UPDATE` dans l'ordre des identifiants contre les interblocages), `writeOff`, `recognize(importContext, tx)` (appelé par la confirmation de Créances), `export()` (CSV RFC 4180, `\n`, `identifiant,type,entite_siren,debiteur_id,factures,montant,motif`, montant en décimal exact construit à partir des centimes, jamais par division flottante, tri par `reference`). Les transitions illégales sont refusées aussi par le déclencheur.

**Batches.** `BatchService.prepare` : `409 batches.no_active_policy` sans version active ; transaction unique : remplace un lot `blocked` du jour (ordres `cancelled`), refuse `409 batches.already_released` si le lot du jour est `ready`, évalue chaque dossier non final par `brain.evaluate` puis `DailyActionService` (décision `daily_action` journalisée avec entrées complètes), construit les ordres (éligibilité, canal et interlocuteur selon `rule-recouvrement-batch-channel-order`, pièces exigées, exclusions comptées par raison), insère les ordres (l'index unique écarte les doublons, comptés), rejoue les témoins (`WitnessReplayer`, lecture seule, aucune écriture hors du résultat du contrôle), calcule les parts et les seuils (`rule-recouvrement-batch-auto-stop`), fixe le statut (`ready` si tout passe, Q-RECOUVREMENT-04 ; sinon `blocked`) et ouvre l'alerte de blocage (une par lot). Un lot de zéro dossier est valide (parts à zéro, aucune division par zéro : le contrôle de part est réussi). `release` n'admet que `blocked`. Les ordres `proposal` d'un lot ne portent jamais d'échéancier tant que le plafond d'encours de la version d'agent et du segment est atteint (`rule-recouvrement-exposure-ceiling`) ; l'ordre `commitment_confirmation` est émis par `OrderService.confirmation` (hors lot, `batch_id` nul), jamais par `prepare`.

**Reviews.** Tirage reproductible exactement selon `rule-recouvrement-review-reproducible` (SHA-256 de chaînes, entiers lus sur 16 hexadécimaux en `BigInt`, tri textuel des identifiants de décision, échange de Fisher-Yates décroissant) ; la fonction est pure et testée contre des vecteurs calculés indépendamment dans le test. Avant relecture, `ReviewItemDto` est construit **sans lire** les colonnes de la décision hors `inputs` (projection explicite).

**Indicators.** Les faits (`indicator_facts`) sont écrits dans la transaction de l'événement qui les produit, un enregistrement par événement (idempotents par `(indicator, source_type, source_id)`) :
- engagement inscrit : fait `commitments` (`a` = 0 tenu, `b` = 1 pris) daté de l'inscription ; engagement tenu : fait séparé (`a` = 1, `b` = 0) daté du constat, rattaché à la politique et à la version d'agent **de l'inscription** (`rule-recouvrement-indicator-commitments`) ;
- engagement tenu avec remise : fait `discounts` (`a` = remise, `b` = montant négociable à l'inscription) daté du constat ;
- réclamation signalée : fait `complaints` (`a` = 1, `b` = 0) ; conversation ouverte : (`a` = 0, `b` = 1) ; ordre d'un lot qui devient `ready` : (`a` = 0, `b` = 1 par ordre, version d'agent nulle) ;
- relecture donnée : fait `errors` (`a` = 1 si désaccord, `b` = 1), politique de la décision relue, version d'agent nulle ;
- horizon atteint (évalué aux points d'évaluation) : fait `collected` (`a` = encaissé, `b` = dû à la première apparition) daté du jour d'horizon ; un dossier dont la première apparition n'avait aucune politique active n'a pas d'horizon (limite assumée de la règle amont).
`GET /indicators` : `GROUP BY` sur le triplet, filtres, période en jours civils Europe/Paris, tri `segment`, `versionDate` décroissante, `agentVersion` (nulls en dernier), pagination `rowFrom`/`rowSize`. Les projections ne contiennent ni identifiant client, ni SIREN, ni coordonnée, ni numéro de facture.

## Règles

Provenance reprise telle qu'écrite en amont. « Où » indique l'endroit d'application principal ; chaque identifiant est cité en commentaire à cet endroit et dans le test qui le couvre.

### Profils et accès (`profiles`, `audit`)
- `rule-recouvrement-profiles-assigned-by-admin` (user) : `PUT /user-profiles/:userId` réservée au rôle `admin` ; sans profil, aucune route de recouvrement n'est ouverte.
- `rule-recouvrement-profile-server-enforced` (user) : `RequireProfile`, lecture en base à chaque requête, avant validation.
- `rule-recouvrement-profile-single` (user, Q-RECOUVREMENT-02 arbitrée par le propriétaire, decision D-0018) : clé primaire sur `user_id`, `PUT` remplace.
- `rule-recouvrement-admin-no-business-access` (user, Q-RECOUVREMENT-01 arbitrée par le propriétaire, decision D-0017) : `RequireProfile` ne regarde pas `role`.
- `rule-recouvrement-agent-channel-required` (user) : validation du `PUT` + CHECK de base.
- `rule-recouvrement-agent-one-per-channel` (user) : index unique partiel.
- `rule-recouvrement-agent-user-role` (inferred) : service + déclencheurs de base.
- `rule-recouvrement-own-profile-locked` (inferred) : service de `PUT`.
- `rule-recouvrement-profile-no-delete` (inferred) : aucune route `DELETE` ; `profile: null`.
- `rule-recouvrement-journal-supervisor` (user) : garde « admin ou superviseur » sur les deux routes du journal (contestation à ouvrir : dossier `audit` gelé).
- `rule-recouvrement-journal-others-refused` (user) : même garde ; l'accès de l'administrateur est conservé.
- `rule-recouvrement-journal-agent-never` (user) : le compte agent n'est ni `admin` ni `supervisor` ; test dédié.

### Dossiers, états, négociation (`cases`, `brain`)
- `rule-recouvrement-cases-supervisor-only` (user) : garde `supervisor` sur les six routes.
- `rule-recouvrement-case-grouping` (user) : un dossier par `debtor_id` (UNIQUE).

## Tests

Jest dans `api/src/features/<feature>/tests/`, contre l'API de test en marche, via `@recouvrement/api-client`, données semées en SQL (comptes dans `base.users` et `base.credentials`, profil dans `base.user_profiles`), `resetData()` en `beforeEach`. Le titre de chaque test cite la règle couverte. Les tests de l'API ne remplacent pas la recette `acceptance/` (propriété de QA).

Cas systématiques pour **chaque route** : nominal ; entrée invalide (chaque borne du contrat : limites, longueurs, énumérations, clés inconnues d'un corps strict) ; `401` sans jeton ; `403 security.access_denied` pour chacun des quatre autres profils, pour un `admin` sans profil et pour un `user` sans profil, **avant** toute validation (un corps invalide avec un mauvais profil donne `403`, pas `400`) ; ressource inconnue ; ressource d'autrui là où la demande en prévoit (aperçu d'un autre superviseur, conversation d'un autre compte agent, dossier d'un autre canal) avec la même réponse que pour l'inexistant.

2. `cases` (tables, états, négociable), `policies` (moteur, contrôles, activation) et les noyaux `decision-queue-core`, `ledger-core`, `disputes-core` (tables et écrivains, sans route).

## Conformité (hors construction)

La demande réserve à un conseil externe, avant tout envoi réel, trois points que ce plan ne tranche pas mais dont il garantit les prérequis techniques : l'annonce de l'IA à l'interlocuteur (AI Act, art. 50) par `aiDisclosureGiven` obligatoire et conservé par conversation ; l'intervention humaine possible pour les familles (RGPD, art. 22) par l'outil `request_human_intervention` et l'élément de file `human_request` ; l'absence de frais ou d'intérêt sur un délai pour une famille par le contrôle d'activation `schedule_limits`. Aucun texte juridique n'est écrit dans le code ni dans les écrans.

## Risques et points relevés

- **R1, journal des appels et annulation d'audit.** Un refus annule la transaction d'audit, donc la ligne de journal d'un refus ne peut pas s'y trouver : d'où `AgentCallFilter` (écriture après annulation). Si le filtre de contrôleur ne reçoit pas les erreurs levées par l'intercepteur de validation (à vérifier tôt par un test), l'écriture se déplace dans un intercepteur enregistré avant le socle.
- **R2, rejeu et audit.** La plateforme écrit une entrée d'audit à toute réponse `2xx` d'une route tracée ; un rejeu en écrit donc une (Q-RECOUVREMENT-19).
- **R3, `Idempotency-Key` sur la lecture.** La demande soumet aussi `GET /agent/cases/:caseId` à la clé et rejoue « l'état enregistré » ; la ligne `agent_calls` d'une lecture conserve donc le corps rendu (taille bornée par la facture de 100 lignes au plus ; à mesurer).
- **R4, charge de l'import.** La cohérence entre lignes d'un même débiteur et la détection de numéro en double demandent une structure par débiteur/numéro ; avec un million de lignes, la table de hachage doit être mesurée (repli : table temporaire indexée en base).
- **R5, `@gorules/zen-engine` natif.** Le module est binaire (napi) : vérifier l'installation sur la machine de fabrication et de test, et fixer un délai d'évaluation par dossier.
- **R6, déclencheur sur `base.users`.** Le refus du passage à `admin` d'un compte agent est une exception SQL non prévue par `PATCH /users/:id` (gelé) : le comportement observable est une erreur du socle ; si la recette attend un code propre, elle doit être précisée (non demandé en amont, donc non construit).
- **R7, `GET /disputes/invoices` face à `GET /disputes/:id`** et les autres routes statiques : l'ordre de déclaration est une exigence de test.
- **R8, `inputs` des décisions.** Elles conservent des entrées complètes (montants, états) ; aucune coordonnée d'interlocuteur n'y est copiée.
- **R9, « par le serveur et par la base ».** Le plan applique les profils par une garde qui lit la base à chaque requête et fait porter par la base les invariants listés en tête de ce document ; il ne crée ni rôle PostgreSQL par profil ni politique de ligne, car l'application se connecte avec un seul rôle (le socle fait de même pour les périmètres). Si le propriétaire entendait des droits SQL distincts par profil, c'est une exigence de plus à arbitrer, non construite ici.
- **R10, l'agent ne peut pas découvrir un `interlocutorId`.** `open_conversation` exige `interlocutorId`, que seul `read_case` rend, et `read_case` exige une conversation ouverte (`rule-recouvrement-agent-ai-disclosure`). Les identifiants d'interlocuteur viendront des ordres d'envoi (versions suivantes) ; dans cette version la recette les connaît par SQL. Rien n'est construit pour lever ce point sans arbitrage (rendre `interlocutorId` facultatif, ou lire sans conversation, changerait la règle de déclaration d'IA).
- **R11, copies de fonctions privées du socle.** `sniff`, la lecture d'en-tête et le décompte des lignes de `ImportsService` sont privés et le dossier est gelé : leur copie dans `WholeFileImportService` est la seule duplication admise de ce plan, commentée et testée par les mêmes cas que le socle (extension contre contenu, en-tête absent, fichier vide).
