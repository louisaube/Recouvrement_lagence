# Demande à l'API : sorties comptables (liste, approbation par lot, export, passage en perte, constat)

Écrans demandeurs : Sorties comptables (listes par état, approbation par lot, export) et Fiche dossier (sorties du dossier, proposition de passage en perte). Besoin : suivre la boucle avec la comptabilité : toute condition accordée qui change un solde produit une sortie, que le superviseur approuve, exporte pour saisie dans l'outil comptable, et que l'import de créances suivant constate. Aucune lecture ni écriture directe dans un outil comptable (version 2).

## Opérations
Toutes les routes : garde de profil `supervisor`. Montants en centimes, dates `AAAA-MM-JJ`. Listes : `from`, `size` (1 à 100, défaut 10), `{ items, total }`.

| Méthode et chemin | Action déclarée | Rôles | Entrée (bornes comprises) | Réponses (codes et formes) |
|---|---|---|---|---|
| `GET /ledger-outputs` | `ledger:list` | profil `supervisor` | `status` : `to_approve` \| `approved` \| `recognized` \| `gap` ; `type` : `discount_credit` \| `write_off` ; `creditor` (SIREN) ; `caseId` uuid ; `from`, `size` | `200 { items: LedgerOutputDto[], total }` triés par `createdAt` décroissant puis `reference` |
| `GET /ledger-outputs/counts` | `ledger:counts` | profil `supervisor` | — | `200 { to_approve, approved, recognized, gap }` (entiers) |
| `POST /ledger-outputs/approvals` | `ledger:approve` | profil `supervisor` | corps strict `{ outputIds: uuid[] }`, 1 à 500 identifiants distincts | `200 { approvedCount: integer }` ; `400 api.validation.incoming_failed` ; `404 repository.not_found` (un identifiant inconnu) ; `409 ledger.not_approvable` (une sortie n'est pas `to_approve`) ; tout ou rien |
| `GET /ledger-outputs/export` | `ledger:export` | profil `supervisor` | — | `200` `text/csv; charset=utf-8` : les sorties `approved`, voir le format ; `Content-Disposition: attachment; filename="sorties-comptables-AAAA-MM-JJ.csv"` |
| `POST /ledger-outputs/write-offs` | `ledger:write-off` | profil `supervisor` | corps strict `{ caseId: uuid, lines: { invoiceId: uuid, amountCents: integer (1..10000000000) }[] (1 à 100, factures distinctes), reason: string (1..500, rogné) }` | `201 { output: LedgerOutputDto }` ; `400` ; `404 repository.not_found` (dossier ou facture inconnus, facture hors dossier) ; `409 ledger.amount_exceeds_balance` ; `409 ledger.case_settled` |

`LedgerOutputDto` = `{ id, reference: string /* ^SC-[0-9]{6,12}$ */, type: 'discount_credit' \| 'write_off', origin: 'commitment' \| 'supervisor', status, creditorSiren, debtorId, caseId, commitmentId: uuid \| null, lines: { invoiceNumber: string, amountCents: integer }[], amountCents, reason: string(1..500), createdAt, approvedBy: { id, email } \| null, approvedAt \| null, recognizedAt \| null, importsSinceApproval: integer, maxImports: integer \| null }`.

Format de l'export (fichier pivot) : première ligne d'en-tête, séparateur virgule, guillemets RFC 4180, fin de ligne `\n`, colonnes dans cet ordre : `identifiant` (la `reference`), `type` (`avoir_remise` \| `passage_perte`), `entite_siren`, `debiteur_id`, `factures` (numéros séparés par « ; »), `montant` (décimal avec point, deux décimales, positif), `motif`. Sans sortie approuvée, le fichier ne contient que l'en-tête (200).

Trace d'audit : `approvals` et `write-offs` sont tracées (types d'objet « Sortie comptable » et « Lot d'approbation » ; actions `ledger:approve` et `ledger:write-off` ; résumés « 12 sorties comptables approuvées. » et « Passage en perte SC-000042 proposé. » ; l'identifiant du lot d'approbation est celui de la première sortie). L'export est une lecture : non tracée.

## Règles
- `rule-recouvrement-ledger-output-creation` (user) : une décision qui modifie un solde produit une sortie comptable : un avoir de remise (`discount_credit`) quand un engagement assorti d'une remise est tenu ; un passage en perte (`write_off`) décidé par le superviseur. Toute sortie naît `to_approve`.
- `rule-recouvrement-ledger-output-content` (user) : chaque sortie porte l'entité créancière (SIREN), le débiteur, les factures concernées avec le montant par facture, le montant total, le motif administratif et un identifiant stable (`reference`, attribuée à la création par une séquence de la base, jamais réutilisée ni modifiée).
- `rule-recouvrement-ledger-output-per-creditor` (inferred) : une sortie ne concerne qu'une entité créancière ; une remise sur un dossier dont les factures viennent de plusieurs entités produit une sortie par entité, la remise étant répartie sur les factures couvertes au prorata de leur solde à l'inscription de l'engagement (reliquat de centimes sur la facture au plus grand solde). Motif d'un avoir de remise : « Remise accordée sur engagement tenu (échéance du JJ/MM/AAAA). » ; d'un passage en perte : le motif saisi.
- `rule-recouvrement-ledger-states` (user) : les états sont `to_approve`, `approved`, `recognized` (Constatée), `gap` (En écart) ; transitions permises : `to_approve → approved` (approbation), `approved → recognized` et `approved → gap` (constat), `gap → recognized` (constat tardif), `gap → approved` (décision « Remettre en attente de constatation »). Aucune autre.
- `rule-recouvrement-ledger-approve-batch` (user) : le superviseur approuve par lot (1 à 500 sorties) ; l'approbation enregistre l'auteur et l'instant ; elle est atomique.
- `rule-recouvrement-ledger-export` (user) : les sorties approuvées sont exportées dans un fichier au format pivot, à saisir dans l'outil comptable ; l'export est répétable et ne change aucun état ; il liste les sorties `approved` (ni `gap`, ni `recognized`).
- `rule-recouvrement-ledger-recognition` (user) : à la confirmation d'un import de créances, chaque sortie `approved` ou `gap` est constatée si l'import la reflète : un avoir portant `reference_sortie` égale à sa référence et de valeur absolue au moins égale à son montant est présent, ou le solde importé des factures concernées est réduit d'autant, c'est-à-dire que la somme sur ses lignes de (solde précédent − paiements affectés depuis − solde importé) atteint son montant. Elle passe alors à `recognized` (`recognizedAt`) et l'élément de file associé se clôt sans décision.
- `rule-recouvrement-ledger-gap` (user) : une sortie `approved` que l'import ne reflète pas voit `importsSinceApproval` augmenter de 1 ; quand il atteint `ledgerMaxImports` de la politique active, elle passe à `gap` et un élément de file `accounting_gap` s'ouvre (un par sortie). `maxImports` est rendu pour affichage (nul sans politique active, auquel cas le compteur seul avance).
- `rule-recouvrement-ledger-not-negotiable` (user) : tant qu'une sortie `approved` ou `gap` n'est pas constatée, le montant négociable la déduit (voir `rule-recouvrement-negotiable-outputs`) ; une sortie `to_approve` ne déduit rien.
- `rule-recouvrement-ledger-write-off-proposal` (inferred) : le superviseur décide un passage en perte depuis la fiche du dossier (sélection des factures et des montants, motif) ; la somme demandée sur une facture, ajoutée à ce que les sorties non constatées couvrent déjà, ne dépasse pas son solde (`409 ledger.amount_exceeds_balance`) ; un dossier `settled` est refusé (`409 ledger.case_settled`). La sortie créée est `to_approve` et suit le même circuit d'approbation.
- `rule-recouvrement-ledger-supervisor-only` (user) : seul le superviseur approuve ; les autres profils reçoivent `403 security.access_denied`.
- `rule-recouvrement-ledger-no-direct-accounting` (user) : aucune route n'écrit ni ne lit dans un outil comptable ; la sortie circule par le fichier exporté et l'import de créances suivant.
- `rule-recouvrement-ledger-audited` (inferred) : approbation et passage en perte sont tracés, jamais l'export ni les lectures.

## Compatibilité
Aucune opération existante modifiée. `reference_sortie` est une colonne facultative du fichier Créances (`imports-recouvrement-api-modification-request.md`). Le type de contenu `text/csv; charset=utf-8` figure dans la liste fermée de `RESPONSE_CONTENT_TYPES` : `@ApiRoute` le déclare avec `schema: z.string()`. `specifications/permissions.yaml` : une ligne par opération.
