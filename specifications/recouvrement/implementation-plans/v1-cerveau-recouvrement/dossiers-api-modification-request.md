# Demande à l'API : dossiers (liste, fiche), montant négociable, engagements, décisions du cerveau

Écrans demandeurs : Dossiers (liste) et Fiche dossier. Besoin : lister et filtrer les dossiers, lire pour un dossier l'état, les factures, les gels, les offres débloquées, les engagements, les sorties comptables, les décisions du cerveau avec leur motif interne et l'historique des transitions ; rechercher une facture (affectation d'un paiement, passage en perte). Les écrans Litiges et Indicateurs n'utilisent pas ces routes. Le cerveau lui-même (évaluation des dossiers, décisions) est du ressort du plan du module ; cette demande en fixe les règles observables.

## Opérations
Toutes les routes : garde de profil `supervisor`. Listes : `from` 0 à 2147483647, `size` 1 à 100 (défaut 10), `{ items, total }`. Montants en centimes (`...Cents`, entiers), dates `AAAA-MM-JJ`, instants ISO.

| Méthode et chemin | Action déclarée | Rôles | Entrée (bornes comprises) | Réponses (codes et formes) |
|---|---|---|---|---|
| `GET /cases` | `cases:list` | profil `supervisor` | `state` (état du référentiel) ; `nature` (`family` \| `company`) ; `segment` (1 à 50) ; `creditor` (SIREN, 9 chiffres) ; `search` (1 à 50 caractères : identifiant client, sous-chaîne sans casse) ; `from`, `size` | `200 { items: CaseSummaryDto[], total }` triés par montant négociable décroissant puis identifiant client ; `400` filtre invalide |
| `GET /cases/filters` | `cases:filters` | profil `supervisor` | — | `200 { segments: string[], creditors: string[] }` (valeurs présentes dans les dossiers, triées) |
| `GET /cases/:id` | `cases:get` | profil `supervisor` | `id` uuid | `200 { case: CaseDetailDto }` ; `404 repository.not_found` ; `400` id mal formé |
| `GET /cases/:id/decisions` | `cases:decisions` | profil `supervisor` | `from`, `size` | `200 { items: DecisionDto[], total }`, du plus récent au plus ancien ; `404` |
| `GET /cases/:id/state-history` | `cases:state-history` | profil `supervisor` | `from`, `size` | `200 { items: StateTransitionDto[], total }`, du plus récent au plus ancien ; `404` |
| `GET /invoices` | `invoices:search` | profil `supervisor` | `number` (1 à 50, préfixe sans casse) obligatoire ; `from`, `size` | `200 { items: InvoiceRefDto[], total }` (factures ouvertes uniquement, solde > 0) triées par numéro ; `400` |

DTO :
- `CaseSummaryDto` = `{ id, debtorId: string(1..50), nature, segment, creditors: string[] /* SIREN, triés */, state, negotiableCents, openBalanceCents, openInvoices: integer, maxDaysLate: integer, updatedAt }`.
- `CaseDetailDto` = `CaseSummaryDto` + `{ debtorSiren: string \| null, invoices: InvoiceDto[], freezes: FreezeDto[], unlockedOffers: UnlockedOfferDto[], commitments: CommitmentDto[], ledgerOutputs: LedgerOutputDto[] /* défini dans sorties-comptables */, openQueueItems: { id, type }[], activePolicy: { id, label } \| null }`.
- `InvoiceDto` = `{ id, kind: 'invoice' \| 'credit_note', number, creditorSiren, amountCents, balanceCents, invoiceDate, dueDate, daysLate: integer, frozen: boolean, freezeCodes: ('dispute' \| 'contestation' \| 'unassigned_payment')[], prescription: 'none' \| 'near' \| 'expired', prescriptionDate: date \| null, coveredByOutputsCents: integer, negotiable: boolean }`.
- `FreezeDto` = `{ code: 'dispute' \| 'contestation' \| 'unassigned_payment', scope: 'invoice' \| 'case', invoiceNumber: string \| null, since, reference: string(1..100) /* motif du litige, référence du paiement */ }`.
- `UnlockedOfferDto` = `{ id, unlockedAt, status: 'current' \| 'superseded' \| 'accepted' \| 'revoked', totalCents, discountCents, installments: { dueDate, amountCents }[], counterpart: { type, deadlineDate \| null, firstPaymentCents \| null } \| null, conversationId: string \| null }`.
- `CommitmentDto` = `{ id, createdAt, status: 'pending' \| 'held' \| 'broken', offerId, totalCents, discountCents, paymentMethod: string, installments: { dueDate, amountCents, paidCents }[], channel, agentVersion: string, conversationId: string }`.
- `DecisionDto` = `{ id, decidedAt, kind: 'daily_action' \| 'offer' \| 'commitment_check' \| 'threshold' \| 'prescription' \| 'exposure_ceiling', outcome: string(1..100), ruleId: string(1..100) \| null, policyVersion: { id, label } \| null, probability: number /* 0 à 1 */, inputs: { name: string(1..100), value: string(0..500) }[], internalReason: { name, value }[], batchId: uuid \| null }`.
- `StateTransitionDto` = `{ at, from: state \| null, to: state, cause: string(1..50), actor: string(1..200) /* « cerveau », « import », e-mail du superviseur, « agent Voix » */, reference: string \| null }`.
- `InvoiceRefDto` = `{ id, caseId, debtorId, number, creditorSiren, balanceCents, frozen: boolean }`.

## Règles
- `rule-recouvrement-cases-supervisor-only` (user) : le profil superviseur voit les dossiers, leur fiche et le motif interne ; le service litiges, le lecteur des indicateurs et le compte agent reçoivent `403 security.access_denied` sur ces routes (le service litiges lit ses propres routes, `litiges-api-modification-request.md`) ; le lecteur des indicateurs n'obtient aucun dossier ni donnée nominative.
- `rule-recouvrement-case-grouping` (user) : un dossier regroupe les factures et avoirs ouverts d'un même débiteur (identifiant client) ; la nature et le segment du dossier sont ceux du débiteur (voir `imports-recouvrement-api-modification-request.md`).
- `rule-recouvrement-debtor-attributes` (user) : un débiteur porte un identifiant client, une nature (famille ou entreprise) et, pour une entreprise seulement, un SIREN ; chaque facture porte l'entité créancière (SIREN) qui l'a émise ; la fiche et la liste les affichent.
- `rule-recouvrement-negotiable-amount` (user) : le montant négociable d'un dossier est la somme des soldes de ses factures (`kind = invoice`) non gelées et non prescrites, diminuée de la part couverte par les sorties comptables approuvées non constatées (`rule-recouvrement-negotiable-outputs`) ; jamais négatif.
- `rule-recouvrement-negotiable-credit-notes` (inferred, default Q-RECOUVREMENT-12) : les avoirs ouverts n'entrent pas dans le montant négociable (seules les factures y entrent) ; ils figurent sur la fiche avec leur solde négatif. (Option B : leur solde, négatif, est ajouté, sans descendre sous zéro.)
- `rule-recouvrement-negotiable-outputs` (user) : tant qu'une sortie comptable approuvée (ou en écart) n'est pas constatée, le montant négociable la déduit et aucune relance ne porte sur la part qu'elle couvre (`coveredByOutputsCents` par facture).
- `rule-recouvrement-invoice-dispute-frozen` (user) : une facture en litige ouvert est gelée et exclue du montant négociable ; une contestation arrête la négociation de tout le dossier (gel de portée dossier) ; un paiement non affecté gèle les dossiers concernés (`imports-recouvrement`).
- `rule-recouvrement-prescription` (user) : pour chaque règle de politique, la date de prescription d'une facture est `point de départ (date de facture ou échéance, selon la politique) + délai de prescription` ; échue (`today ≥ date`), la facture sort du montant négociable (`prescription: expired`) et un élément de file `prescription_expired` s'ouvre (un par facture) ; à partir de `date − délai d'alerte` (`near`), un élément `prescription_near` s'ouvre avec l'étape suivante proposée dans ses détails, une fois par facture.
- `rule-recouvrement-amount-threshold` (user) : si le montant négociable dépasse le `thresholdCents` de la règle du dossier, la négociation s'arrête et un élément `amount_over_threshold` s'ouvre (un seul élément ouvert par dossier et motif) ; les outils des agents répondent `409 negotiation.stopped`.
- `rule-recouvrement-case-state-referential` (user) : les états, leurs précédences et les transitions permises sont celles de `referentiel-etats-et-transitions.md` ; une transition hors du tableau n'est jamais produite.
- `rule-recouvrement-state-transitions-logged` (user) : chaque transition d'état est journalisée (instant, de, vers, cause, acteur, référence) dans la même transaction que l'événement qui la provoque ; `GET /cases/:id/state-history` les rend.
- `rule-recouvrement-family-transfer-never-executed` (user) : le cerveau n'exécute jamais le transfert à l'étape suivante d'un dossier de famille : il le propose (élément `transfer_proposed`) et seul le superviseur le décide.
- `rule-recouvrement-decision-journal` (user) : chaque décision du cerveau journalise ses entrées complètes, la version de politique, la règle appliquée et sa probabilité (1 tant que la table de décision est déterministe) ; elle est rendue par `GET /cases/:id/decisions`, jamais modifiée ni supprimée.
- `rule-recouvrement-internal-reason-private` (user) : le motif interne (règle, version, montants de référence) reste au journal des décisions, lisible du seul superviseur ; ni l'agent ni le débiteur n'en reçoivent rien.
- `rule-recouvrement-evaluation-points` (inferred) : aucun ordonnanceur n'existe dans cette version ; les dossiers sont évalués (prescription, seuil, engagements tenus ou rompus, gels, état) à la confirmation d'un import de créances, de paiements ou de litiges, à la préparation d'un lot, à chaque appel d'outil d'agent sur le dossier, à la clôture d'un litige et à chaque décision du superviseur. Un événement du temps (échéance d'un engagement, seuil de prescription) est donc constaté au premier de ces événements qui le suit. La date du jour est la date civile du fuseau Europe/Paris.
- `rule-recouvrement-commitment-held` (user) : un engagement est tenu quand les paiements affectés aux factures qu'il couvre, datés d'après l'engagement, atteignent son montant au plus tard à la date promise (pour un échéancier : à chaque échéance, le cumul affecté atteint le cumul dû) ; le dossier revient à `open` (ou passe à `settled` s'il ne reste aucune facture ouverte) et, si l'engagement accorde une remise, une sortie comptable `discount_credit` est produite (`sorties-comptables-api-modification-request.md`).
- `rule-recouvrement-commitment-broken` (user) : un engagement dont un versement est manqué à sa date (à l'évaluation suivant la date, cumul affecté inférieur au cumul dû) est rompu : déchéance, ses offres débloquées passent à `revoked` (les concessions tombent, la négociation reprend à l'ancrage), le dossier revient à `open` et à l'action fixée par la politique (décision `commitment_check` journalisée).
- `rule-recouvrement-commitment-covers-negotiable` (inferred) : un engagement couvre les factures négociables du dossier au moment de son inscription ; ses lignes (facture, montant) sont conservées.

## Compatibilité
Aucune opération existante modifiée. `LedgerOutputDto` est défini par `sorties-comptables-api-modification-request.md`. Les routes ne sont pas rattachées à un périmètre (`scope_code` absent des tables métier) : l'accès repose sur les profils. `specifications/permissions.yaml` : une ligne par opération, garde de profil `supervisor`.
