# Coverage - version `socle-renfort-recette`

Acceptance files (black box, HTTP + SQL): `acceptance/acceptance-renfort-login-body.test.ts`, `acceptance/acceptance-renfort-logs.test.ts`, `acceptance/acceptance-renfort-token.test.ts`; helpers in `acceptance/renfort-helpers.ts` (raw HTTP so that header values reach the server untouched, forged tokens, read of the test server log). Tests of previous versions and `harness.ts` are unchanged.

This version adds no route, no schema, no error code and changes no permission: `specifications/permissions.yaml` is left unchanged (no operation added or modified, no `cross_owner_tests`; ownership is `none` for every exercised operation). Operations exercised: `POST /auth/login`, `GET /auth/current-user`, `POST /users`, `GET /users`.

The rules below already exist in the specifications (`10-plateforme.md`, `20-authentification-session.md`, `30-comptes.md`, `98-arbitrages.md`); the version only verifies them. Several tests are expected to pass already (the version comes from a mutation test): they are legitimate non-regression tests. The test most likely to fail before correction is the strict reading of the `Authorization` header (point 4).

| Rule id | Point | Coverage |
|---|---|---|
| `rule-foundation-login-single-error` | 1 | API: `acceptance-renfort-login-body` - unreadable hash (empty, arbitrary text, `$2b$10$tropcourt`, altered valid hash) gives 401 `security.invalid_credentials`, body byte-for-byte equal to a wrong password, keys `status`/`code`/`message`, no token, no `Set-Cookie`, in token mode and in browser mode (current-user stays `{}`); witness: neighbouring account logs in. |
| `Q-PLAT-04` | 2 | API: same file - 1 MiB + 1 byte gives 413 `api.payload_too_large` on `POST /auth/login` and `POST /users` (admin); just under the limit gives no 413; malformed JSON (truncated, trailing comma, non-JSON) gives 400 `api.validation.incoming_failed`; server still serves afterwards. |
| `Q-PLAT-01` | 2 | API: same file - error body keys limited to `status`, `code`, `message` (+ `details` for validation), no stack, file path or `node_modules`; row counts of `base.users`, `base.credentials`, `base.audit_logs` unchanged after a refused `POST /users`. |
| `rule-foundation-user-create-fields`, `rule-foundation-no-self-signup` | 2, 3 | API: used as the anchor of the `POST /users` refusals (nothing written; anonymous stays 401, simple user gets no account). Their own behaviour is covered by earlier versions. |

| `rule-foundation-session-expired` | 4, 5 | API: `acceptance-renfort-token` - `Authorization` other than exactly `Bearer <token>` (extra word, two tokens, `Basic`, `Token`, bare token, `Bearer` alone, leading space, tab, trailing space; "two spaces" was removed by version `socle-bearer-rfc6750`, which now accepts several spaces) gives 401 `security.invalid_token` on `GET /auth/current-user` and `GET /users`, not rescued by a valid cookie; exact form accepted (witness). Token HS512, HS384, `alg: none` (with and without trailing dot), same claims and secret, refused in header and in cookie; witness: same claims re-signed in HS256 with the secret from `api/.env.test` accepted (proves the secret is right). | `rule-foundation-session-persists` | 4 | API: same file - the session cookie, alone, among other cookies (first, middle, last, with or without spaces after `;`, leading space) or as issued at browser login, authenticates `GET /auth/current-user`; a cookie with another prefix, another host, a longer or prefixed name, another name, no value or a blank value, or sent with an Origin of another host, does not (200 `{}`). |

Not observable through the API: the unit tests of the developer (`failed query` exception filter, `tokenSource` forms) in `api/src/platform/tests/`; they do not replace this suite.

Assumptions (from the plan): the case of the word `Bearer` is not asserted; a body too large on a protected route without authentication stays 401 (only 401 for malformed JSON is asserted); the log is the file `api/.server-test.log` written by `scripts/server/start.sh`.
